AI AUTOMATION UI
SOFTWARE REQUIREMENTS SPECIFICATION (SRS)

Date: 2026-09-06
Version: 0.2
Status: Draft

===============================================================================
1. PURPOSE
===============================================================================

The initial application will be a trading journal generator focused on futures
trading.

The first supported instruments are:

- MES — Micro E-mini S&P 500 Futures
- MGC — Micro Gold Futures

The application will automate generation of the user's daily trading journal
using structured daily market levels, instrument configuration, marked-up chart
screenshots, and the user's existing trading framework.

Real-time market monitoring and trade alerts are future capabilities and are not
required for V1.


===============================================================================
2. V1 SCOPE
===============================================================================

V1 must allow the user to:

1. Select a supported instrument.
2. Enter daily market levels.
3. Add and upload marked-up chart screenshots as needed.
4. Assign a timeframe to each chart screenshot.
5. Generate a daily trading journal.
6. Review the generated journal.

Initial supported instruments:

- MES
- MGC

Required daily level inputs:

- PDH
- PDL
- ONH
- ONL
- Settlement

Chart inputs are dynamic. The user may add only the chart screenshots needed
for a journal rather than being required to populate a fixed set of chart
upload fields.

Initial standard chart timeframe options:

- 5-minute
- 15-minute
- 1-hour
- 4-hour
- Daily

The chart screenshots may be the same marked-up charts prepared by the user for
daily trading.


===============================================================================
3. JOURNAL GENERATION REQUIREMENTS
===============================================================================

The journal generator must use:

- Selected instrument
- Instrument configuration
- PDH
- PDL
- ONH
- ONL
- Settlement
- User-supplied chart screenshots and their assigned timeframes
- Existing trading framework/rules

The entered numerical market levels are authoritative structured values even
when the same levels appear visually on uploaded charts.

The application must identify each chart's timeframe from the timeframe assigned
to that chart rather than requiring AI to infer the timeframe from the image.

The journal analysis must apply the existing trading framework consistently and
must not introduce new trading criteria during analysis.


===============================================================================
4. INSTRUMENT REQUIREMENTS
===============================================================================

MES and MGC must be available as predefined instruments.

Each instrument must be capable of having its own configuration, including as
needed:

- Symbol
- Name
- Exchange
- Tick size
- Tick value
- Time zone
- Session definitions
- Settlement configuration

The user should not need to enter static instrument/session configuration during
normal daily journal preparation.

The user will enter the daily Settlement price in V1.

The design must allow additional instruments to be added in the future without
changing the behavior of existing instruments.


===============================================================================
5. APPLICATION MODES
===============================================================================

The application must distinguish between:

- Development mode
- Live mode

Application mode must be independent of the selected market-data source.

Development mode may expose diagnostic and testing information.

Live mode should present only the information needed for normal application use.


===============================================================================
6. DATA SOURCE REQUIREMENTS
===============================================================================

The application must distinguish between market-data sources.

Planned sources:

- Manual
- Mock
- Live API (future)

V1 normal operation will use Manual data.

Mock data will support development and repeatable testing.

Live API data is deferred until a financially and technically suitable futures
market-data provider is identified.

Application mode and data source must remain separate concepts.


===============================================================================
7. DEVELOPMENT / TESTING REQUIREMENTS
===============================================================================

Development mode may provide access to:

- Loaded instrument configuration
- Current data source
- Raw journal request
- Raw AI response
- Validation errors
- API status
- API usage and estimated request cost
- Detailed errors
- Mock test scenarios
- Intermediate/calculated values

Mock data should support repeatable known MES/MGC scenarios.

The same test scenario should be reusable after code changes to help validate
that existing behavior has not unintentionally changed.


===============================================================================
8. FUTURE REQUIREMENTS — NOT V1
===============================================================================

The following capabilities are explicitly deferred:

- Real-time futures market-data integration
- Automatic PDH calculation
- Automatic PDL calculation
- Automatic ONH calculation
- Automatic ONL calculation
- Automatic Settlement retrieval/calculation
- Native live charting
- Real-time rules evaluation
- BUY alerts
- SELL alerts
- SMS notifications
- Historical market replay
- Add Instrument user interface
- User-defined/custom chart timeframes
- Persistent custom chart timeframe configuration
- Persistent storage of chart images
- Persistent/searchable journal history

Automated brokerage order execution is not currently part of project scope.

Future trade automation is intended to produce alerts only. The user remains
responsible for placing trades.


===============================================================================
9. API SECURITY AND COST CONTROL REQUIREMENTS
===============================================================================

AI/API credentials and other secrets must not be stored in or exposed by the
React browser application.

External API communication requiring credentials must be handled through an
appropriate backend service.

API usage must include safeguards against unexpected or excessive costs.

The application must:

- Use provider-level project/account spending limits when available.
- Prevent accidental duplicate or concurrent journal-generation requests.
- Avoid automatic retries that could unintentionally create additional
  billable API requests.
- Handle API quota, budget, and rate-limit failures cleanly.
- Track API usage information needed to estimate the cost of each journal
  generation.

Development mode should expose API usage diagnostics when available, including:

- AI model used
- Input token usage
- Output token usage
- Number of chart images submitted
- Estimated request cost

API usage and cost must be measured during development before AI journal
generation is considered ready for Live mode.


===============================================================================
10. REAL-TIME DATA FEASIBILITY REQUIREMENT
===============================================================================

Before implementing real-time futures functionality, available providers must be
evaluated for:

- MES support
- MGC support
- Real-time availability
- Historical availability
- OHLCV/bar intervals
- Settlement data availability
- API access
- Personal/nonprofessional licensing
- CME/COMEX fees
- Monthly cost
- Reliability
- Documentation quality
- Streaming support if required

Real-time integration must not block development of the V1 journal generator.

===============================================================================
END OF SRS
