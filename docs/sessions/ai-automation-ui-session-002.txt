===============================================================================
PRODUCT DIRECTION ESTABLISHED
===============================================================================

The original concept was a broader AI automation interface.

The immediate V1 direction is now more specific:

TRADING JOURNAL GENERATOR

Initial supported instruments:
- MES
- MGC

The application should automate generation of the daily trading journal using
the existing trading framework.

Real-time market monitoring, BUY/SELL alerts, SMS notifications, and live
charting remain possible future capabilities but are deferred.

===============================================================================
V1 DAILY JOURNAL WORKFLOW
===============================================================================

Planned normal workflow:

1. Select instrument.
2. Enter daily market levels.
3. Upload marked-up charts already prepared for daily trading.
4. Generate the daily journal.
5. Review the generated journal.
6. Add save/export/history functionality later as requirements are defined.

Required daily numerical inputs:

- PDH
- PDL
- ONH
- ONL
- Settlement

Required chart inputs:

- 15-minute chart
- 1-hour chart
- 4-hour chart

The user already marks up these charts for normal daily trading, so V1 should
use those same screenshots rather than requiring a second chart-preparation
workflow.

The numerical market levels remain separate structured inputs even when they
are visible on the chart. They serve as authoritative values rather than
requiring AI to read precise prices from image pixels.

===============================================================================
SCREENSHOT / MARKET DATA DECISION
===============================================================================

Screenshots are useful for V1 because they provide visual context such as:

- Price structure
- Candles
- EMA 9 / EMA 21
- MACD
- Volume
- Marked daily levels
- Higher-timeframe context

Screenshots are not intended to become a permanent technical dependency.

If economical programmatic market data becomes available later, the application
may obtain the underlying data directly.

Native charts may still be useful in a future version so the user can visually
validate what the application/rules engine is evaluating.

===============================================================================
INSTRUMENT CONFIGURATION DECISION
===============================================================================

MES and MGC should be PRECONFIGURED rather than repeatedly configured by the
user.

Instrument-specific information should live in configuration/data rather than
being scattered through journal logic.

Conceptual configuration includes:

- Symbol
- Name
- Exchange
- Tick size
- Tick value
- Time zone
- Session definitions
- Settlement configuration

Static instrument information must remain separate from daily market data.

Daily market data includes:

- Date
- PDH
- PDL
- ONH
- ONL
- Settlement price
- Chart images

The user should enter the daily Settlement PRICE but should not need to enter
settlement/session times every morning.

Exact session and settlement definitions must be verified before finalizing the
instrument configuration.

===============================================================================
FUTURE ADD-INSTRUMENT DESIGN
===============================================================================

The application should eventually support additional instruments without
changing or risking existing MES/MGC behavior.

Conceptual future UI:

[MGC] [MES] [+ Add Instrument]

Adding an instrument should primarily add a new instrument configuration rather
than require changes to the journal engine.

The Add Instrument UI itself is not part of the immediate V1 implementation.

===============================================================================
DATA SOURCE ARCHITECTURE
===============================================================================

The application should own a standardized internal market-data format.

Provider-specific response formats should eventually be translated through an
adapter.

Conceptual architecture:

External Provider
        |
        v
Provider Adapter
        |
        v
Application Standard Data Format
        |
        +--> Journal Engine
        +--> Rules Engine (future)
        +--> Chart Engine (future)

This allows a future data provider to be changed without rewriting the rest of
the application.

Planned data sources:

MANUAL
- V1 normal source.
- User enters levels and supplies charts.

MOCK
- Development/testing source.
- Provides controlled repeatable scenarios.

LIVE API
- Future source.
- Deferred pending market-data feasibility/cost research.

===============================================================================
APPLICATION MODE DECISION
===============================================================================

Application Mode and Data Source are separate concepts.

Application Mode:
- Development
- Live

Data Source:
- Manual
- Mock
- Live API

Examples:

Development + Mock
Development + Manual
Development + Live API
Live + Manual
Live + Live API

This allows real provider data to be debugged in Development mode later without
coupling debugging behavior to the data source.

===============================================================================
DEVELOPMENT MODE
===============================================================================

Development mode may eventually expose information such as:

- Loaded instrument configuration
- Current data source
- Raw journal request
- Raw AI response
- Validation errors
- API status
- Detailed errors
- Mock scenario selection
- Intermediate/calculated values

Live mode should hide developer/debugging information and show only the normal
daily-use interface.

===============================================================================
REAL-TIME MARKET DATA — DEFERRED
===============================================================================

Real-time futures market data was identified as a major project dependency.

Webull OpenAPI and other providers may require separately licensed futures data.
The cost and licensing could materially affect whether real-time automation is
financially worthwhile.

Decision:

DO NOT allow real-time market data to block V1.

Future research remains required for:

- MES availability
- MGC availability
- Real-time data
- Historical data
- OHLCV/bar intervals
- Settlement information
- API access
- Personal/nonprofessional licensing
- CME/COMEX fees
- Monthly cost
- Reliability
- Documentation
- Streaming support

Providers discussed for future investigation include:

- Webull OpenAPI
- CME data/API services
- Databento
- Other futures-data providers

===============================================================================
FUTURE LIVE CHART / ALERT CONCEPT
===============================================================================

If financially feasible, a future version may include native marked-up live
charts with instrument tabs.

Potential chart content:

- Candlesticks
- EMA 9
- EMA 21
- MACD
- Volume
- PDH / PDL
- ONH / ONL
- Settlement
- Entry / Stop / Targets
- Setup/status annotations

Important design principle:

The future chart and future rules engine should consume the SAME underlying
market data so the user can visually validate the engine's conclusions.

Longer-term alert concept:

Market Data
    |
    v
Rules / Analysis Engine
    |
    v
Setup Validation
    |
    +--> BUY Alert
    +--> SELL Alert
    |
    v
SMS Notification

Automated brokerage order execution is NOT currently part of scope.

The intended future system is alert-only.
